# Задание 1. Анализ и планирование


### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.
- Система поддерживает подключение отопления только в режиме личного визита к пользователю


**Мониторинг температуры:**

- Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.
- Система поддерживает мониторинг температуры с датчиков, установленных в домах.


### 2. Анализ архитектуры монолитного приложения

Язык программирования Go.
База данных: PostgreSQL
Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
Взаимодействие: Синхронное, запросы обрабатываются последовательно.
Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
Развертывание: Требует остановки всего приложения.


### 3. Определение доменов и границы контекстов

Домены как бизнес-процессы это:
1. Управление устройствами умного дома
2. Поддержка подключения к экосистеме партнерских бизнесов

Поддомены:

1. Управление отоплением
2. Управление светом
3. Управление воротами
4. Удаленное наблюдение за домом
5. Самостоятельное подключение устройств и наладка сценириев их работы
6. Просмотр телеметрии (мониторинг)
7. Будущее неуточненное поведение

Границы контекстов (вычленение контекста на основе бизнес-логики, хранения данных, UI для пользователя
и фоновых задач, если есть. Этот подход получен из АИ-ассисента Яндекс-Практикума по запросу какая методика вычленения ограниченного контекста):
1. Контекст управления отоплением: 
бизнес-функция (функциональное требование): просматривать текущую температуру в своих домах
UI пользователя: веб-интерфейс
2. Контекст управления светом: 
бизнес-функция: включать и выключать свет
UI пользователя: веб-интерфейс
3. Контекст управления воротами: 
бизнес-функция: запирать и отпирать автоматические ворота
UI пользователя: веб-интерфейс
4. Контекст удаленного наблюдения за домом: 
бизнес-функция не определена 
UI пользователя: веб-интерфейс
5. Контекст самостоятельного подключения устройств и наладки сценариев их работы:
бизнес-функция: 
1) регистрация нового устройства в своем профиле 
2) программирование системы по каждому устройству
UI пользователя: веб-интерфейс (интернет-канал)
6. Просмотр телеметрии
бизнес-функция: Мониторинг для всех устройств
UI пользователя: веб-интерфейс

Контексты могут пересекаться следующим образом:
1. База данных: Контактные данные о пользователях, о доме где находятся не связанные между собой устройства являются общими для всех устройств.
2. Единая система мониторинга всех устройств

Контексты могут быть разделены на отдельные базы данных, одна для мониторинга другая для данных пользователей и регистрации датчиков. Таким образом высокая нагрузка на базу мониторинга отделена и не будет мешать. Вторая база может просто быть поделена на отдельные схемы (в начале второго спринта я видела пример где базы физически отдельны и для корзины и для пользователей и тд, но не очень понятно насколько это целесообразно)


### **4. Проблемы монолитного решения**

Потенциальные проблемы:
Возросшее количество устройств и пользователей может создавать нагрузку на базу данных где пользователями регистрируются устройства.
Самостоятельная установка так же потребует новых интерфейсов и хранения данных которые должны масштабировать имеющуюся систему (чтобы разграничить ее по типам датчиков.)

Альтернатива:
Отделить телеметрию (большая нагрузка) от базы данных юзеров и устройств.
Не уверена достаточно ли на уровне только схем в одной базе данных разделить устройства от пользователей или прямо отдельную физическую только для пользователей и отдельно для всех устройств и отдельно для телеметрии.

Минус нескольких физических баз это поддержка и дополнительные эндпойнты.
Плюс это скорость доступа при нагрузке.
.--> Посоветовалась с чатомГПТ какую стратегию в таком случае лучше выбрать.
Чтобы остановиться на конкретном варианте, далее буду использовать подход:
* База данных для телеметрии
* База данных для устройств и юзеров, где отдельные схемы для устройств и регистрации юзеров с домами

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```
